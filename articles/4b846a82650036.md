## Enumeration

### Nmap

まずはNmapでポートスキャンを行う。

```sh
┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# nmap -Pn -sSV -n -r -T4 10.129.30.85 -oN nmap_top1000.log
Starting Nmap 7.99 ( https://nmap.org ) at 2026-07-05 15:05 +0000
Nmap scan report for 10.129.30.85
Host is up (0.63s latency).
Not shown: 997 closed tcp ports (reset)
PORT    STATE SERVICE VERSION
22/tcp  open  ssh     OpenSSH 8.9p1 Ubuntu 3ubuntu0.3 (Ubuntu Linux; protocol 2.0)
80/tcp  open  http    nginx/1.18.0 (Ubuntu)
443/tcp open  https?
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel

Service detection performed. Please report any incorrect results at https://nmap.org/submit/ .
Nmap done: 1 IP address (1 host up) scanned in 99.94 seconds
```

`-sSV`: SYNスキャン＋Versionスキャン
`-Pn`: Pingチェック無効化
デフォルトだとPingが通らないとスキャンが始まらないが、このチェックを省略し若干の時短を図る
`-n`: 名前解決無効化。同じく時短目的
`-r`: ポートスキャンを昇順に行う。特に意味はない、好み
フルポートスキャン中にWiresharkなどで覗き見した際に、いまどこまで回っているかを確認するために使用することが多い
`-T 4`: 並列スキャン数増加。未指定時はデフォルトの3が選択される、時短
`-oN`: 結果を保存するファイル名を指定

空いているのは22(ssh)、80(http)、443(https)の3つ。まずは情報量が多そうな80から見ていく。

### 80/http

> 80/tcp  open  http    nginx/1.18.0 (Ubuntu)

Webサービスが稼働してるらしいので、実際にアクセスし画面を確認する。

`keeper.htb`というドメインを持っているそうなのでhostsに追加する。

```sh
┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# echo "10.129.30.85 keeper.htb" | sudo tee -a /etc/hosts
Password:
10.129.30.85 keeper.htb
```

何かのログイン画面が表示される。

![Request Trackerのログイン画面](https://static.zenn.studio/user-upload/b7a9b3e99e5d-20260707.png)

調べてみると Request Tracker の管理画面のよう。

:::details Request Trackerとは？
読み方: リクエストトラッカー
正式名称: Request Tracker (RT)
意味: Best Practical社が開発するオープンソースのチケット/問い合わせ管理システム。メールやWeb経由で寄せられた問い合わせを「チケット」として管理する。ヘルプデスクの現場でよく使われる。
:::

Request Trackerのデフォルト認証情報(`root:password`)がドキュメントに載っていたので、そのままログインを試すとそのままログインが通ってしまった。実務でもたまにある。内部にしか公開してないシステムの場合だとよくある印象。

![Request Trackerの管理ダッシュボード](https://static.zenn.studio/user-upload/9f90fa684f5e-20260707.png)

ユーザ一覧を確認すると`lnorgaard`というユーザがおり、さらにチケットのコメント欄にそのユーザのパスワードが平文で書き込まれているのを確認。

![チケットコメントに平文で記載されたパスワード](https://static.zenn.studio/user-upload/3bfd23879110-20260707.png)

```txt:creds.txt
lnorgaard:Welcome2023!
```

:::message
初期パスワードが変更されないまま運用されており、管理画面に誰でもログインできる状態だった。
よって、デフォルト認証情報の脆弱性を突いて管理画面に侵入し、さらにチケット本文へ平文で書かれた認証情報を回収できた状況(認証情報の不適切な管理)。
:::

## Foothold

回収した`lnorgaard`の認証情報でSSHログインを試す。

:::details sshとは？
読み方: エスエスエイチ
正式名称: Secure Shell
意味: 暗号化された通信路を通じてリモートホストにログインし、コマンドを実行するためのプロトコル/ツール。22番ポートが定番。
:::

```sh
┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# ssh lnorgaard@keeper.htb
lnorgaard@keeper.htb's password:
Welcome to Ubuntu 22.04.3 LTS (GNU/Linux 5.15.0-78-generic x86_64)

 * Documentation:  https://help.ubuntu.com
 * Management:     https://landscape.canonical.com
 * Support:        https://ubuntu.com/advantage
Failed to connect to https://changelogs.ubuntu.com/meta-release-lts. Check your Internet connection or proxy settings

You have mail.
Last login: Sun Jul  5 00:17:51 2026 from 10.10.14.234
lnorgaard@keeper:~$ id
uid=1000(lnorgaard) gid=1000(lnorgaard) groups=1000(lnorgaard)
```

`lnorgaard`としてログインできた。ホームディレクトリの`user.txt`を取得する。

```sh
lnorgaard@keeper:~$ cat user.txt
```

:::message
Footholdは、管理画面から回収した平文パスワードがOSアカウントでも使い回されていたことによる。認証情報の使い回し / 平文管理が突破口となった。

取得した認証情報は、他サービスへ横断的に試すのは実務でもよくある。ただし、実質的なパスワードスプレーはロックアウトを誘発しやすいので、対象アカウント数・試行間隔をコントロールし、事前合意の範囲で行う。
:::

:::details .dmp / .kdbx とは？
読み方: ダンプ / ケーディービーエックス
意味(.dmp): メモリダンプファイル。プロセスのメモリ内容がそのまま保存されており、平文パスワードなどが残っている場合がある。
意味(.kdbx): パスワード管理アプリ KeePass のパスワードデータベースファイル。中身は暗号化されており、開くにはマスターパスワードが必要。
:::

KeePassium(KeePass互換アプリ)で`passcodes.kdbx`を開こうとしたが、マスターパスワードが必要だった。

![KeePassiumでマスターパスワードを要求される](https://static.zenn.studio/user-upload/90988b506dae-20260707.png)

`KeePassDumpFull.dmp`を手掛かりに検索すると`CVE-2023-32784`がヒット。PoCがGitHubにあるので実行する。

:::details CVE-2023-32784とは？
読み方: シーブイイー
意味: KeePass 2.x で、ユーザが入力したマスターパスワードの平文がプロセスメモリ上にほぼそのまま残ってしまう脆弱性。メモリダンプから、最初の1文字を除くパスワードのほぼ全体を復元できる。
:::

![PoC出力の欠番部分](https://static.zenn.studio/user-upload/18c2e4c4458e-20260707.png)

:::details なぜ料理名だと当たりを付けたのか
PoCが復元できるのはASCII文字だけで、`ø`や`é`のような非ASCII文字は歯抜けになる。歯抜けの位置(2文字目・6文字目あたり)と「dgr...d med flde」という並びから、`ø`を補うと自然な語になる言語を探すと、デンマーク語の定番デザート「rødgrød med fløde」にぴったり一致した。
:::

料理名を使って`.kdbx`を開く。`Rødgrød med fløde`はダメだったが、先頭を小文字にした`rødgrød med fløde`で開けた。中身はPuTTY形式の秘密鍵と、rootのパスワードだった。

```txt:creds.txt
lnorgaard:Welcome2023!
root:F4><3K0nd! // new!
```

このパスワードでそのままrootログインを試したが通らなかった。

```sh
┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# ssh keeper.htb

root@keeper.htb's password:
```

![rootでのパスワード認証が拒否される](https://static.zenn.studio/user-upload/24c7094515c9-20260707.png)

`.kdbx`に入っていたPuTTY鍵(.ppk)をOpenSSH形式に変換して使う。`puttygen`というユーティリティで変換できる。

:::details puttygenとは？
読み方: パティージェン
意味: SSHクライアント PuTTY に付属する鍵生成・変換ユーティリティ。PuTTY独自形式(.ppk)の秘密鍵を、OpenSSHが読める形式へ変換できる。
:::

PuTTY公式ドキュメント[^1]を見ながら変換し、生成した鍵ファイルでSSHする。

```sh
┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# puttygen putty.ppk -O private-openssh -o privatekey.pem

┌──(root㉿5602a1b7889d)-[~/Keeper]
└─# ssh -i privatekey.pem keeper.htb

 * Documentation:  https://help.ubuntu.com
 * Management:     https://landscape.canonical.com
 * Support:        https://ubuntu.com/advantage

You have new mail.
Last login: Tue Aug  8 19:00:06 2023 from 10.10.14.41
root@keeper:~# id
uid=0(root) gid=0(root) groups=0(root)
```

Pwn3d!

この `.ppk` はパスフレーズ無しでOpenSSH形式に変換が可能だったため、秘密鍵のパスフレーズ必須化は推奨対策として挙げられる。

:::message
権限昇格は、脆弱なバージョンのKeePass(パッチ未適用の脆弱性 / CVE-2023-32784)によるマスターパスワード漏えいと、KeePass内に平文保管されていたroot鍵・認証情報(認証情報の不適切な管理)の組み合わせによって成立した。
:::

## まとめ

改めて攻撃チェーンを整理すると以下の通り。

1. Nmapで80/httpを発見し、`keeper.htb`をhostsに追加してRequest Trackerの管理画面を特定
2. RTのデフォルト認証情報(`root:password`)でログインし、管理画面を掌握
3. チケットのコメント欄に平文で書かれた`lnorgaard`のパスワードを回収
4. 同じパスワードがSSHでも使い回されており、`lnorgaard`としてログイン(user.txt)
5. ホームディレクトリに置き忘れられた`RT30000.zip`を入手し、KeePassのメモリダンプ(.dmp)とDB(.kdbx)を発見
6. CVE-2023-32784でメモリダンプからマスターパスワードを部分復元し、歯抜け部分をデンマーク料理名(`rødgrød med fløde`)と推測して確定
7. `.kdbx`からrootのPuTTY秘密鍵を入手し、`puttygen`でOpenSSH形式に変換してrootログイン(root.txt)

PoCの結果で出てきたのが英語っぽいけどそうじゃないよくわからん文字列だったので、外れたかーなんて思ってたけどあってるんかい。

Webにデンマーク語がデフォルト言語に設定されたユーザがいたような気がするけどこういうことだったのか・・
ちなみにHTBなのでやらないですが、実務では後始末もやっています。
